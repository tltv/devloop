# Vaadin + Spring Boot app — dev loop

Make the change, get it into the running app, verify it in the browser with Playwright.
A clean compile is not evidence the UI renders what you intended — only the browser is.

```
src/main/java/                              views + services (pure Java, no HTML/JS)
src/main/resources/META-INF/resources/      the app's CSS and icons
src/main/resources/application.properties   config (server.port, Vaadin settings)
src/main/frontend/generated/                generated by the build — never edit
../demo-shared/src/main/                    a sibling library module the app depends on
```

This app is one module of a Maven reactor, and it depends on the sibling `demo-shared`
module like any library. A `spring-boot:run` started inside `demo-app` resolves
`demo-shared` from the local Maven repository, so an edit there is invisible until that
module is rebuilt and installed — see *Making a change live*.

Maven commands run from this directory via the Bash tool (`./mvnw`) or PowerShell
(`mvnw.cmd`). Add `-o` (offline) once dependencies are cached — it saves several seconds per
command. `-q` keeps output to errors only.

## Running the app

`spring-boot:run` blocks, so start it in the **background** with its output in a log, then
wait for the ready line — never poll blindly:

```bash
./mvnw -o spring-boot:run > target/app-run.log 2>&1          # run_in_background: true
until grep -qE "Started Application|BUILD FAILURE" target/app-run.log; do sleep 2; done
```

Ready in ~10–15 s (`Started Application in 9.5 seconds`). App URL: **http://localhost:8080**
(unless `server.port` says otherwise). `spring-boot:run` recompiles Java **and** re-copies
resources first, so it is the only command you need to make a change live.

**Stopping is by port, not by the wrapper.** Killing the `mvnw` shell leaves the forked JVM
holding 8080:

```powershell
Get-NetTCPConnection -LocalPort 8080 -State Listen -ErrorAction SilentlyContinue |
  ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

Always stop before starting again — a second app cannot bind 8080 and fails in a way that
looks like a code error. Don't use `spring-boot:start`/`stop`; the goal forks the app but can
hang without returning.

## Making a change live

| Change | Do this | Cost |
|---|---|---|
| CSS/icons under `META-INF/resources/` | `./mvnw -o -q resources:resources`, then reload the page in Playwright | ~3 s |
| Java, `application.properties`, anything else | stop the app, start it again, reload the page | ~15 s |
| Java or CSS in `../demo-shared/` | from the repository root: `mvn -o -q install -pl demo-shared` (the wrapper only exists in `demo-app/`), then stop and start the app | ~25 s |

There is **no hot reload** in this setup: a plain `spring-boot:run` serves what is in
`target/classes`, so an edit that is not copied or compiled there is invisible, no matter how
many times you reload.

Saving CSS makes Vaadin's file watcher reload the browser by itself — **don't trust it**. It
reloads before you have copied anything, so the page comes back with the old style and looks
like your edit did nothing. Copy first, then reload yourself. (On Windows the watcher's
in-place update also throws `InvalidPathException` into the app log before falling back to
that reload; it is noise from your own save, not a fault to fix.)

**Check Java compiles before paying for a restart** — 5 s instead of a failed 15 s start:

```bash
./mvnw -o -q compile      # exit 0 = clean; exit 1 prints file:[line,col] and the symbol
```

## Verifying with Playwright

1. `browser_navigate` to the app URL.
2. **The first snapshot is usually empty** — Vaadin renders client-side after the initial
   response. Wait for a known element or re-snapshot before asserting.
3. Assert the thing you changed:
  - **CSS — by computed style**, not screenshots:
    `() => getComputedStyle(document.querySelector('.app-name')).fontSize`
  - **Java — by rendered DOM**; component text lives in the light DOM:
    `() => [...document.querySelectorAll('vaadin-button')].map(b => b.textContent.trim())`
4. Check `browser_console_messages` (a `/favicon.ico` 404 is normal noise).

Reload the page after every restart or `resources:resources` — nothing is pushed to an open
page. If a tool call returns *"Target page, context or browser has been closed"*, call
`browser_close` once, then navigate again. Dev mode injects Vaadin's dev-tools/Copilot
toolbar; ignore those nodes and never assert on them. Snapshots and screenshots land in
`.playwright-mcp/` (untracked scratch).

## Also

- `./mvnw test` — unit + UI tests.
- Use the **Vaadin MCP server** (`search_vaadin_docs`, `get_component_java_api`,
  `get_component_styling`, `get_theme_css_properties`) instead of recalling API from memory;
  check the Vaadin version in `pom.xml`. Prefer theme CSS properties (`--vaadin-*`, `--aura-*`)
  over hard-coded values.
