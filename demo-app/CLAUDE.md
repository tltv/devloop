# Vaadin + Spring Boot app — dev loop

Change code or CSS with `./vaadin-dev`, then verify it in the browser with Playwright.
`apply` proves the bytes are live; only the browser proves the UI renders what you intended.

```
src/main/java/                              views + services (pure Java, no HTML/JS)
src/main/resources/META-INF/resources/      the app's CSS and icons
src/main/resources/application.properties   config
src/main/frontend/generated/                generated by the build — never edit
target/devloop/app.log, daemon.log          logs
```

## `vaadin-dev`

A **bash script** — run it with the **Bash tool** (Git Bash), never PowerShell, from the
directory that contains it. A daemon auto-spawns on first use, owns the app process, and
survives between commands, so every command answers for the same running app.

| Command | What it does |
|---|---|
| `./vaadin-dev status [--json]` | app up? registered? dev server? last transaction |
| `./vaadin-dev start` | launch the app in dev mode (~30 s cold); blocks until it serves or fails |
| `./vaadin-dev apply [--json]` | make the edits on disk live; blocks until Stable or Failed |
| `./vaadin-dev restart` | stop + start (needed after config changes) |
| `./vaadin-dev stop` / `shutdown` | stop the app / stop the daemon too |

**Never run `./mvnw spring-boot:run`** — the daemon owns the app; a second process fights it
for the HTTP port.

`apply` finds the change-set itself by scanning `src/main/java` and `src/main/resources`. Run
it once after a batch of edits, not per file.

## The cycle

1. `./vaadin-dev status` — if `stopped`, `./vaadin-dev start`.
2. Edit Java and/or CSS.
3. `./vaadin-dev apply` — **exit code is the verdict**: `0` live, `1` failed, `4` superseded.
4. Verify in the browser. Only then report the change as working.

### Reading `apply`

```
hmr: 1 resource(s) copied, pushed 1 stylesheet(s) in place    ← CSS, pushed into the open page
hot-reload: redefineClasses(1); onHotswap completed=true      ← Java, hot-swapped, UI refreshed
compiling → runtime → restarting → Stable                     ← app restarted; reload the page
compiling → Failed
  Foo.java:51:53  error: cannot find method bar() in class Foo
  → check the name, or add the missing member/import          ← fix, re-apply; app keeps last good bytes
```

`--json` gives `outcome`, `classification`, `changeSet`, `diagnostics[]`
(`file`/`line`/`column`/`message`/`hint`), `timings`, `nextAction`.

| Edit | Browser |
|---|---|
| CSS/icons under `META-INF/resources/` | updates in place, **no reload** |
| Java method bodies, string literals, most view code | updates in place, **no reload** |
| Structural Java (new fields/beans, new repository methods, changed routes or annotations) | restart → **reload the page** |
| `application.properties` | copied only — run `./vaadin-dev restart` to take effect |
| Hand-written `src/main/frontend/` files | not watched; start with `VAADIN_DEV_DAEMON_OPTS="-Dvaadin.frontend.hotdeploy=true" ./vaadin-dev start` |

## Verifying with Playwright

App URL: **http://localhost:8080** (unless `server.port` says otherwise).

- **Navigate once, keep the page open across applies.** CSS pushes and Java hot-swaps land in
  an already-open page; re-navigating hides what you are testing. Reload only after a restart.
- **The first snapshot after `browser_navigate` is usually empty** — Vaadin renders
  client-side. Wait for a known element or re-snapshot before asserting.
- **CSS: assert computed style**, not screenshots —
  `() => getComputedStyle(document.querySelector('.app-name')).fontSize`
- **Java: assert the rendered DOM** — component text is in the light DOM:
  `() => [...document.querySelectorAll('vaadin-button')].map(b => b.textContent.trim())`
- Check `browser_console_messages` after a change (a `/favicon.ico` 404 is normal noise).
- Dev mode injects Vaadin's dev-tools/Copilot toolbar — ignore those nodes, never assert on them.

## When it goes wrong

- `compiling → Failed` — diagnostics name file, line, column. Fix and re-apply.
- `frontend-down` — Vite stopped answering: `./vaadin-dev restart`.
- App failed to start (a taken port, a bad config) → `start` exits `1` and names the reason
  from the app's own log, with the tail printed under it; `status` repeats the reason. The
  whole log is `target/devloop/app.log`. Daemon wedged → `./vaadin-dev shutdown`, then any
  command respawns it.

## Also

- `./mvnw test` for unit + UI tests.
- Use the **Vaadin MCP server** (`search_vaadin_docs`, `get_component_java_api`,
  `get_component_styling`, `get_theme_css_properties`) instead of recalling API from memory;
  check the Vaadin version in `pom.xml`. Prefer theme CSS properties (`--vaadin-*`, `--aura-*`)
  over hard-coded values.
